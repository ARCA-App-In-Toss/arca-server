# 회원 (member)

## 회원과 익명 키

- 회원은 앱인토스 익명 키 주체 하나에 묶인다. 익명 주체당 회원은 1명이다
- 같은 익명 키로 세션을 교환하면 기기와 관계없이 같은 회원을 받는다. 판정은 `auth.md`를 따른다
- 서버는 익명 키 원문 대신 그 해시로 회원을 찾는다

## 가입

`GUEST` 세션으로 필수 약관에 동의하면 회원이 생긴다. 이 성공이 가입 완료다.

- 허용 세션 mode는 `GUEST`다. `ACTIVE` 세션의 요청은 403이 아니라 항상 `409 MEMBER_ALREADY_EXISTS`다
- 요청마다 아래 순서로 판정하고, 처음 걸린 조건의 오류로 응답한다
  1. `ACTIVE` 세션이면 `409 MEMBER_ALREADY_EXISTS`
  2. 세션의 익명 키에 이미 회원이 있으면 `409 MEMBER_ALREADY_EXISTS` (가입 전에 다른 기기에서 받아 둔 GUEST 토큰 등)
  3. 동의 검증. 규칙은 `terms.md`를 따른다 (`422 POLICY_VERSION_CHANGED`, `422 CONSENT_REQUIRED`)
  4. 회원 생성과 동의 기록
- 오류로 끝나면 회원, 동의 기록, 세션 모두 바뀌지 않는다
- 회원 생성과 동의 기록은 한 트랜잭션이다. 닉네임은 가입에 포함하지 않는다 (가입 직후 닉네임은 `null`)
- 서버가 회원 코드를 배정한다
  - 형식은 `ARCA-` 뒤에 대문자 영어와 숫자 5자를 무작위로 붙인 값이다 (예: `ARCA-7K2QX`)
  - 회원마다 다르다. 이미 있는 코드가 나오면 다시 뽑는다
- 내부 섹션은 아직 배정하지 않는다. 배정 규칙이 정해지는 공유 기능에서 추가한다. 섹션은 응답에 넣지 않는다
- 실명, 전화번호, 이메일, 생년월일은 받지 않는다
- 성공하면 가입에 쓴 GUEST 토큰을 폐기하고 새 `ACTIVE` 토큰을 발급한다. 성공 응답은 `201` 하나뿐이다
  - 응답이 유실돼 같은 요청을 다시 보내면 GUEST 토큰이 폐기돼 `401 SESSION_RECOVERY_REQUIRED`다. 클라이언트는 재전송하지 않고 세션을 재교환하며, `ACTIVE`면 가입된 것이다
- 같은 익명 키의 가입이 동시에 와도 UNIQUE 제약으로 하나만 저장된다. 경쟁에서 진 요청은 DB 예외로 `500 DATABASE_ERROR`다. 중복 제출은 프론트가 버튼 비활성화로 막는다

## 회원 정보 조회

- 허용 세션 mode는 `ACTIVE`, `GUEST`다. `GUEST` 세션은 403이 아니라 항상 `404 MEMBER_NOT_FOUND`다
- 회원 코드, 닉네임을 돌려준다. 이 값이 현재 profile의 정본이다
- 조회는 데이터를 만들지 않는다

## 닉네임

- 허용 세션 mode는 `ACTIVE`다
- 닉네임 규칙을 어기면 `422 NICKNAME_INVALID`이고 닉네임이 바뀌지 않는다
- `nickname`이 `null`이면 닉네임을 해제한다. 필드를 생략하면 `400 INVALID_REQUEST`다
- 닉네임 규칙 (문자열일 때)
  - 앞뒤 공백을 제거한 값을 저장하고 검사한다
  - 확장 grapheme cluster 기준 2~12자다. 결합 이모지(👨‍👩‍👧)는 1자다
  - 한글, 영문, 숫자, 중간 공백, 이모지를 허용한다. 중복을 허용하고 금칙어 검사는 없다
  - 줄바꿈, 제어 문자, 서식 문자(ZWSP 등 보이지 않는 문자)를 거절한다. 단 결합 이모지를 이루는 ZWJ(U+200D)와 태그 문자(U+E0020~U+E007F)는 허용한다
  - 보이지 않는 한글 채움 문자(U+115F, U+1160, U+3164, U+FFA0)와 점자 공백(U+2800)을 거절한다
  - 공백 제거 후 UTF-16 길이가 255를 넘으면 거절한다 (결합 문자를 이어 붙인 비정상 입력 방지)
- 성공 응답은 바뀐 뒤의 회원 profile이다
- 같은 닉네임으로 다시 설정해도 성공한다
- 회원 profile에는 revision(낙관적 잠금)이 없다. 다른 기기에서 동시에 온 변경은 따로 막지 않고 나중 것이 남는다

## 모든 데이터 삭제

회원이 자신의 데이터를 모두 지우고 떠난다. 되돌리는 기능은 없다.

- 허용 세션 mode는 `ACTIVE`다. `GUEST` 세션은 `403 SESSION_SCOPE_INSUFFICIENT`다
- 성공하면 아래를 한 트랜잭션으로 처리하고 body 없이 `204`로 응답한다
  - 그 회원의 답변을 모두 지운다
  - 회원 profile(회원 코드, 닉네임)을 지운다
  - 동의 기록을 지우고 동의 증빙을 남긴다. 증빙 규칙은 `terms.md`를 따른다
  - 그 회원의 아직 유효한 토큰을 모두 폐기한다. 폐기 범위는 `auth.md`를 따른다
- 하나라도 실패하면 모두 rollback되고 `500 INTERNAL_ERROR` 또는 `500 DATABASE_ERROR`다. 답변, 회원, 동의 기록, 토큰이 모두 그대로 남고 증빙은 남지 않는다
- 삭제 뒤 같은 토큰으로 오는 요청은 `401 SESSION_RECOVERY_REQUIRED`다. 같은 키로 세션을 재교환하면 `GUEST`다
  - 응답이 유실되면 클라이언트는 다시 보낸 요청의 `401 SESSION_RECOVERY_REQUIRED`나 재교환 결과(`GUEST`면 삭제됨)로 확인한다
- 같은 익명 키로 다시 가입하면 새 회원 코드를 가진 새 회원이 생긴다. 삭제 전 답변과 합치지 않는다
  - 그 익명 키 주체의 원시 분석 이벤트를 지우고 `all_data_deleted` 일별 집계를 1 늘린다. 규칙은 `analytics.md`를 따른다
- 동시 요청은 따로 막지 않는다. 실제 문제가 보이면 그때 보완한다
  - 같은 토큰으로 삭제가 동시에 두 번 오면 하나만 성공한다. 진 요청은 시점에 따라 `404 MEMBER_NOT_FOUND` 또는 `500 DATABASE_ERROR`다. 중복 제출은 프론트가 버튼 비활성화로 막는다
  - 삭제 중 같은 회원의 답변 작성이 끼면 둘 중 하나가 `500 DATABASE_ERROR`로 끝나고 그 요청은 통째로 rollback된다. 일부만 지운 상태는 생기지 않는다
